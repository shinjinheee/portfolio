## 3. 디자인 토큰

### 컬러 (PSD 추출값)

```css
:root {
  --blue-700: #0674CD;   /* 버튼 hover, 강조 텍스트 */
  --blue-600: #0886D3;   /* 브랜드 프라이머리 */
  --blue-50:  #EAF4FC;   /* 연한 배경 */
  --orange:   #FF812E;   /* 액센트, 단 하나의 포인트 */
  --ink-900:  #343843;   /* 본문 최상위 */
  --ink-600:  #5F6470;   /* 서브 텍스트 */
  --ink-400:  #9AA0AB;   /* 캡션, 메타 */
  --line:     #E9EEF2;   /* 구분선, 카드 테두리 */
  --surface:  #F8F9FB;   /* 섹션 배경 */
  --white:    #FFFFFF;
}
```

오렌지는 **페이지당 1회만** 사용한다. 기존 PSD에서도 푸터 원형 버튼 하나뿐이었고, 그게 정확한 판단이다.

### 타이포

| 역할 | 폰트 | 크기 / 굵기 | 자간 |
|---|---|---|---|
| Display | Space Grotesk Medium | 88 / 1.1 | -0.02em |
| H1 (케이스 제목) | Pretendard Bold | 56 / 1.25 | -0.02em |
| H2 (섹션 제목) | Pretendard SemiBold | 40 / 1.3 | -0.015em |
| H3 (블록 제목) | Pretendard SemiBold | 28 / 1.4 | -0.01em |
| Lead (한 줄 결론) | Pretendard Medium | 24 / 1.6 | -0.01em |
| Body | Pretendard Regular | 18 / 1.75 | 0 |
| Caption / Meta | Pretendard Regular | 15 / 1.6 | 0 |
| Eyebrow | Space Grotesk Medium | 14 / 1.2 | 0.08em, 대문자 |

영문 헤드라인은 Space Grotesk, 한글 본문은 Pretendard. 기존 PSD와 동일한 조합이다.

### 그리드 · 간격

```
컨테이너   max-width 1600px, 좌우 여백 60px
컬럼       12칼럼, gutter 24px
섹션 간격  상하 패딩 160px (모바일 80px)
블록 간격  64px
요소 간격  8 / 16 / 24 / 40 (4px 배수)
radius     카드 16px, 버튼 8px, 이미지 12px
```

### 4-2. 메타 바 (케이스 페이지 필수)

모든 케이스 페이지 H1 바로 아래 고정. **참여도 기재 요건을 충족하는 유일한 지점이므로 예외 없이 넣는다.**

```
┌──────────┬──────────┬──────────┬──────────┬──────────┐
│ 유형     │ 기간     │ 역할     │ 참여도   │ 툴       │
│ 실무     │ 2025.03– │ UX 설계  │ 기획 100 │ Figma    │
│          │ 2026.05  │ UI 제작  │ 디자인100│ ProtoPie │
└──────────┴──────────┴──────────┴──────────┴──────────┘
5칼럼 균등, 배경 --surface, radius 16px, 패딩 32px 40px
라벨 Caption/--ink-400, 값 Body/--ink-900
```

개인 과제는 `유형` 칸에 `개인 과제`로 표기하고 제작 시점을 병기한다.

### 4-3. 섹션 헤더

```
EYEBROW                          ← Space Grotesk, --blue-600
섹션 제목이 들어갑니다            ← H2
한 줄 요약 문장이 들어갑니다.     ← Lead, --ink-600
```

### 4-4. As-is / To-be 비교 블록

케이스 페이지 전반에서 반복 사용하는 핵심 컴포넌트.

```
┌───────────────────────┐  ┌───────────────────────┐
│ AS-IS                 │  │ TO-BE                 │
│ ┌───────────────────┐ │  │ ┌───────────────────┐ │
│ │                   │ │  │ │                   │ │
│ │      이미지        │ │  │ │      이미지        │ │
│ │                   │ │  │ │                   │ │
│ └───────────────────┘ │  │ └───────────────────┘ │
│ 무엇이 문제였는지      │  │ 무엇을 바꿨는지        │
└───────────────────────┘  └───────────────────────┘
   6칼럼, 배경 --surface        6칼럼, 배경 --blue-50
   라벨 --ink-400               라벨 --blue-700
```

### 4-5. 지표 카드

```
┌─────────────────┐
│ 검증 포기율      │  ← Caption, --ink-400
│ 73%             │  ← Space Grotesk 64px, --blue-600
│ 해소            │  ← Body, --ink-600
│ ─────────────── │
│ 측정: 어드민     │  ← 12px, --ink-400
│ 대시보드 로그    │
└─────────────────┘
```

**측정 근거 줄은 반드시 넣는다.** 숫자만 크게 띄우면 면접에서 첫 질문이 "이거 어떻게 쟀나요"가 되고, 답이 카드에 이미 있으면 그 질문이 신뢰로 바뀐다.

### 4-6. 푸터

기존 PSD 그대로 유지. 파란 배경 + `Work With ME` + 오렌지 원형 버튼.

수정 사항:
- PDF 링크 라벨 정정 (`포트폴리오 PDF` / `경력기술서 PDF`)
- 경력기술서 PDF 링크 추가
- `SHINJINHEE © 2026`로 연도 갱신

## 6. 케이스 페이지 공통 템플릿

`case-*.html` 4개는 같은 골격을 쓴다.

```
Header
─────────────────────────────
Hero        Eyebrow / H1 / 한 줄 결론 / 대표 이미지
Meta bar    유형·기간·역할·참여도·툴
─────────────────────────────
01 Context      제품·환경이 무엇인지
02 Problem      관찰 데이터 (가장 두꺼운 섹션)

**섹션 번호 규칙** — `01 / 02 …`는 실제로 순서가 의미를 갖는 경우에만 쓴다. 문제 정의에서 검증까지는 순서가 논리 그 자체이므로 번호를 붙이는 게 맞다. 홈이나 아카이브에는 붙이지 않는다.

**좌측 고정 목차** — 케이스가 길어지므로 화면 왼쪽에 스크롤 연동 목차를 둔다. 폭 200px, `position: sticky`, 현재 섹션 --blue-600.

## 7. 케이스별 개별 스펙

### 7-1. case-payment.html — 결제 단말 리디자인

메인 케이스. 가장 두껍게 만든다.

```
Hero            매장에서 촬영한 결제 단말 사진 (풀블리드 16:9)
Meta            개인 과제 / 2026.08–09 / 문제 정의·UX·UI·UT / 100%

01 Context      대상 단말 소개, 관찰 장소와 기간
02 Problem      ┌ 현장 관찰 기록 (사진 + 메모 그리드 3열)
                ├ 결제 실패 유형 분류표
                └ 페인포인트 3~4개 카드
03 Hypothesis   As-is 플로우 다이어그램 → 문제 구간 하이라이트
04 Solution     비교 블록 ×3
                ├ 승인 대기 구간
                ├ 실패 원인별 분기
                └ 재시도 · 영수증 처리
05 Result       UT 설계와 결과 (표본 수 명시)
06 Retro        실무 경험이 판단에 어떻게 작용했는지
```

**정직성 원칙 두 가지**

1. UT 수치는 개인 과제의 자체 검증임을 명시한다. `n=8` 같은 표본 수를 반드시 적는다. 실무 지표와 같은 무게로 보이게 만들지 않는다
2. 유니바 화면을 기억으로 재현하지 않는다. 관찰 대상은 공개된 매장 단말이어야 한다

**유니바 경험이 들어가는 자리는 `02 Problem`과 `06 Retro`다.** "결제 단말을 안에서 다뤄본 사람만 아는 것"이 문제 정의의 깊이로 나타나고, 회고에서 그 출처를 밝힌다. 화면이 아니라 판단으로 증명하는 구조다.

### 7-2. case-bx.html — UNIVA CI 개편

```
Hero            개편 후 브랜드 적용 이미지
Meta            실무 / UNIVA / BX 방향 정의·심볼·가이드라인 / 범위별 %

01 Context      회사가 어떤 전환기에 있었는지
02 Problem      개편 전 브랜드가 말하던 것과 실제 사업의 간극
03 Hypothesis   재정의한 브랜드 방향 (한 문장 + 근거)
04 Solution     ┌ 심볼 · 로고타입
                ├ 컬러 시스템
                ├ 타이포그래피
                └ 적용 규칙 (최소 여백, 오사용 예시)
05 Result       공개 적용 사례 — 웹사이트, 전시 부스, 보도자료
06 Retro        일관성 유지에서 어려웠던 점
```

**자료 조달 방법** — 원본 파일이 없으므로 공개 자산에서 수집한다.

- 유니바 웹사이트 (개편 전후 비교)
- 전시 부스 사진: FIX 2024, 베트남 ICTComm, CES 2026, 월드 IT쇼 2026
- 보도자료 이미지
- 제피 제품 페이지의 브랜드 적용

**표기 규칙**
- 개편 전 CI를 비교로 쓸 때 출처 명시
- 캡처 이미지는 출처와 촬영 시점 병기
- 참여도를 범위별로 쪼개서 기재 (`BX 방향 100% / 심볼 ○○% / 가이드라인 100%`)

가이드라인 문서는 없지만, 공개된 결과물에서 적용 규칙을 역으로 정리해 보여주는 것은 문제없다. 이미 세상에 나와 있는 로고의 사용 규칙을 다시 그리는 것이기 때문이다.

### 7-3. case-ds.html — 디자인 시스템 · 토큰

```
Hero            토큰 구조 다이어그램
Meta            실무 / UNIVA / 토큰 설계·Variables·명세 / 100%

01 Context      PD·FE 핸드오프가 어떻게 돌아가고 있었나
02 Problem      스타일 값 재확인 요청이 반복되던 실제 대화 캡처

**용어 통일이 필요하다.** 현재 경력기술서는 "Base→Semantic 2-tier 컬러 토큰", 기존 포트폴리오는 "3레이어 구조"로 쓰고 있다. 두 문서를 나란히 보는 심사자가 헷갈린다.

> 컬러 토큰은 2-tier, 구축 프로세스는 3단계

이 표현으로 모든 문서를 통일한다.

**40% 수치 처리** — 지표 카드 하단 근거 줄에 측정 방식을 그대로 적는다. 실무자 설문과 디자인 QA 건수 합산이라는 점을 숨기지 않는 편이 오히려 신뢰를 얻는다.

### 7-4. case-zephy.html — ZEPHY

기존 PDF의 4개 케이스를 2개로 압축한다.

```
Hero            서비스 플로우 다이어그램
Meta            실무 / UNIVA / UX 설계·UI·PRD·QA / 참여도

01 Context      ZEPHY가 무엇이고 누가 쓰는가
02 Problem      기능은 늘었지만 작업이 이어지지 않던 구조
03~05 메인 1    답변과 근거의 단절 → 검증 포기율 73% 해소
03~05 메인 2    운영자와 제어권의 단절 → 개발 리소스 16시간 → 0
06 그 외 개선   업로드 이탈 23%→8%, 편집 진입 27초→1초
                (각 3~4줄 요약 + 썸네일 1장씩)
07 Retro        기존 회고 유지
```

메인 2건은 성격이 서로 달라야 한다. 하나는 사용자 신뢰(73%), 하나는 운영 구조(16시간→0). 비슷한 성격의 개선을 두 개 나열하면 한 개만 보이는 효과가 난다.

GS인증 1등급은 `05 Result` 하단에 외부 검증 배지로 배치한다.

## 12. 제출 전 체크리스트

**필수 요건**

- [ ] 모든 케이스 페이지에 메타 바가 있고 참여도가 기재되어 있다
- [ ] 개인 과제와 실무가 라벨로 명확히 구분되어 있다
- [ ] 지표마다 측정 방식이 함께 적혀 있다

**기술**

- [ ] `file://`로 index.html을 열어도 모든 페이지가 정상 동작한다
- [ ] 참조하는 CSS·JS 파일이 전부 존재한다
- [ ] 웹폰트가 로컬에 임베드되어 있다 (사내망 차단 대비)
- [ ] 외부 CDN 의존이 없다
- [ ] zip 20MB 이하
- [ ] PHP 인클루드 제거 완료

**내용**

- [ ] 라온시스 재직 기간이 세 문서에서 동일하다
- [ ] 디자인 시스템 용어가 통일되어 있다 (2-tier / 3단계)
- [ ] 아카이브 연도 태그와 실제 날짜가 일치한다
- [ ] "Human-cecntered", "경북귀어귀촌지원샌터" 등 오타가 없다
- [ ] `og:url`, `og:title`, `og:description`이 채워져 있다
- [ ] 푸터 PDF 링크 라벨과 실제 파일이 맞다
- [ ] 전 직장 플랫폼으로 향하는 외부 CTA가 없다
- [ ] 저작권 문제가 될 자료가 없다
